
The libei capture backend tears down and recreates its whole InputCapture session in
three cases where the portal spec expects reuse:

1. barrier updates — the mutter workaround at `libei.rs:49`
2. `SeatRemoved`/`DeviceRemoved` (`libei.rs:558`) — the "GNOME kills the session on
   device changes" workaround at `:460`
3. via 2: any host keymap change. EIS keymaps are immutable per device, so compositors
   do keymap changes as device remove/re-add. I remap keys in an enter/leave hook, so I
   get a full session recreate on every crossing — 30 crossings came out to 34
   ConnectToEIS calls in a 2h session.

Both workarounds run on every compositor, not just GNOME. The spec wants one long-lived
session: ZonesChanged says to call GetZones + SetPointerBarriers again on the same
session, and after Release the session stays enabled.

On Hyprland 0.56 + xdg-desktop-portal-hyprland 1.4.0 this churn hits a compositor-side
session leak (filed: https://github.com/hyprwm/xdg-desktop-portal-hyprland/issues/419) that eventually kills the whole desktop session. That's
their bug, but even without it, recreating costs a full
CreateSession/ConnectToEIS/GetZones/SetPointerBarriers/Enable round trip at the moment
you're crossing screens.

Proposal: keep one session for the process lifetime. On ZonesChanged, re-set barriers on
the existing session. On DeviceRemoved, rebind the replacement device instead of
cancelling. Keep the mutter workarounds but gate them — detect the desktop, or only fall
back to recreate when reusing the session actually fails. Can work on a PR if the
approach sounds right.
