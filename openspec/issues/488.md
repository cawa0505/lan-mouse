## Summary

Mutual-TLS (DTLS) handshake between two `lan-mouse` peers consistently fails with a **fatal `Bad Certificate` alert**, sent by the server side immediately after receiving the client's `Certificate` + `CertificateVerify` message. Reproduced on both the released `0.11.0` build and a fresh build of latest `main` (`392af44`). Confirmed via packet capture that this is a genuine protocol-level rejection, not a network/firewall/routing issue.

## Environment

- Two Arch Linux machines on the same LAN (both Hyprland/wlroots, `layer-shell` capture backend, `wlroots` emulation backend)
- `lan-mouse` 0.11.0 (Arch `extra` package) and self-built `main` @ `392af44`
- `webrtc-dtls = 0.12.0`, `rcgen = 0.13.2` (from `Cargo.lock`)
- Both peers' `authorized_fingerprints` verified to exactly match the live certs (checked byte-for-byte both directions)

## Steps to reproduce

1. Configure two machines as mutual `lan-mouse` peers (`[[clients]]` with matching `position`/`ips`, cross-authorized `authorized_fingerprints`)
2. Trigger a real input-capture crossing (moving the cursor to the configured screen edge) so the client attempts to connect
3. Client logs: `failed to connect to <ip>:4242: Alert is Fatal or Close Notify`

## Packet capture

Captured on the connecting (client) side with `tshark -i <iface> -f "udp port 4242"`. The handshake proceeds through `ClientHello` → `HelloVerifyRequest` → `ClientHello` (with cookie) → `ServerHello, Certificate, ServerKeyExchange, CertificateRequest, ServerHelloDone` → client's `Certificate, ClientKeyExchange, CertificateVerify, ChangeCipherSpec, EncryptedHandshakeMessage` — and the server then immediately replies with a fatal alert:

```
1  0.000000  10.x.x.x   → 229.x.x.x  DTLS      Client Hello (SNI=ignored)
2  0.000610  229.x.x.x  → 10.x.x.x   DTLSv1.2  Hello Verify Request
3  0.000655  10.x.x.x   → 229.x.x.x  DTLSv1.2  Client Hello (SNI=ignored)
4  0.001433  229.x.x.x  → 10.x.x.x   DTLSv1.2  Server Hello, Certificate, Server Key Exchange, Certificate Request, Server Hello Done
5  0.001853  10.x.x.x   → 229.x.x.x  DTLSv1.2  Certificate, Client Key Exchange, Certificate Verify, Change Cipher Spec, Encrypted Handshake Message
6  0.002555  229.x.x.x  → 10.x.x.x   DTLSv1.2  Alert (Level: Fatal, Description: Bad Certificate)
7  0.002610  10.x.x.x   → 229.x.x.x  DTLSv1.2  Alert (Level: Fatal, Description: Bad Certificate)
```

This exact sequence repeats identically on every retry (~1/sec), byte-for-byte the same failure point every time.

## What I ruled out

- **Firewall**: both hosts have an explicit `ufw` rule allowing UDP/4242 between them; raw `nc`-based UDP packets pass cleanly in both directions on the same path.
- **Routing/MTU**: MTU 1500 throughout, single-switch LAN, confirmed symmetric routing after fixing an unrelated multi-homing issue on one host.
- **Clock skew / cert validity**: both hosts' clocks in sync; `rcgen`-issued certs are valid `1975–4096`.
- **Stale/corrupt certificate**: regenerated fresh certificates on *both* peers (deleted `lan-mouse.pem`, let the daemon regenerate, re-authorized new fingerprints) — identical `Bad Certificate` failure with brand new keys.
- **Version mismatch**: reproduced with both peers running the *identical* freshly-built commit (`392af44`).
- **Simultaneous connection race**: reproduced with the non-connecting peer's client fully deactivated (`lan-mouse cli deactivate`), so only one side was ever attempting a handshake.

## Workaround

Building and running the last pre-DTLS release (`v0.10.0`, before encryption was introduced) works reliably with the same two machines and the same LAN path — mouse/keyboard sharing works immediately with no certificate involved. This strongly points at the DTLS/certificate-verification path specifically (likely in how the client's `CertificateVerify` is generated or verified against the `rcgen`-issued self-signed cert), rather than anything network- or config-related.

Happy to provide the raw `.pcap`, run further tests, or try patches — this took a lot of narrowing down and I'd like to help get it fixed upstream.
